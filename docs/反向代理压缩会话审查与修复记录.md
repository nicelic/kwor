# 反向代理压缩会话审查与修复记录

## 审查范围

本记录复核了两份历史会话：一份从“HTTPS 数据包压缩算法”开始的技术问答与实现记录，以及后一份对该实现进行修复的会话记录。审查不把历史会话中的“已完成”描述当作事实，而是逐项对照当前工作区源码、依赖快照、测试和 RFC 文本重新确认。

审查日期为 2026 年 8 月 22 日。当前项目不是 Git 仓库，本记录只以工作区实际文件和可复现命令为依据，不依赖 Git 状态或提交历史。

## RFC 核对结论

本次重点核对了以下规范：

| 规范 | 本次采用的结论 |
| --- | --- |
| RFC 9110，`Accept-Encoding`、qvalue、`identity`、`*`、`Vary`、`Content-Encoding` | 没有 `Accept-Encoding` 字段时，协议语义把任意内容编码视为可接受；显式空字段表示不希望内容编码。RFC qvalue 通常是 `0` 或 `1` 加上最多三位小数，不能接受 `NaN`、指数形式或正负号；本项目为满足固定优先级，额外接受 `0..1` 范围内任意精度的小数，并只把 q=0 当作拒绝。`identity` 默认可接受，但可由显式 `identity;q=0` 或适用的 `*;q=0` 排除。服务器在没有可接受表示时应返回 406。 |
| RFC 7694 | 请求实体使用不支持的 `Content-Encoding` 时，可用响应中的 `Accept-Encoding` 告知该资源接受的请求编码；项目现在返回 415，并列出六种项目支持的编码。 |
| RFC 9659 | HTTP `zstd` 的标准互操作窗口建议与项目策略分开评估；本项目当前按用户要求把 zstd 窗口上限提高到不超过 36 MiB 的最大合法值 32 MiB。这个窗口上限和解压后实体总量上限是两个不同的限制，不能互相替代。 |
| RFC 8878 | Zstandard 基础格式与编码参数来源；项目使用 `klauspost/compress` 的纯 Go 实现。 |
| RFC 7932 | Brotli 的格式和编码语义来源；项目通过本地 `andybalholm/brotli` 快照提供 `br`。 |
| RFC 9846（取代 RFC 8446）、RFC 7457 | 当前 TLS 1.3 规范要求 `legacy_compression_methods` 使用 null 压缩方法；TLS 压缩、CRIME 类侧信道与 HTTP 内容编码不是同一层的问题。应用层压缩仍需单独评估 BREACH 等动态秘密泄露风险。 |

## 历史会话中的错误或过度表述

### 1. “HTTPS 的压缩算法”表述不准确

HTTPS 是 HTTP over TLS 的组合，不是一个独立的压缩算法。当前项目涉及的压缩主要是 HTTP 内容编码：请求使用 `Content-Encoding`，响应使用 `Content-Encoding`，客户端通过 `Accept-Encoding` 表达可接受编码。TLS 加密发生在这些 HTTP 字节之后，不能把“TLS 层压缩”和“HTTP 内容压缩”混写。

### 2. TLS 压缩、CRIME、BREACH 需要分开

历史会话把 TLS 压缩、CRIME 和 HTTP 内容压缩的关系讲得过于绝对。当前 TLS 1.3 规范（RFC 9846，取代 RFC 8446）没有可协商的非空压缩方式；旧 TLS 版本的压缩风险是协议层问题。CRIME 主要讨论 TLS/协议压缩与秘密数据的长度侧信道，BREACH 则与 HTTP 响应压缩和动态秘密混合有关。关闭 TLS 压缩并不自动消除所有 HTTP 压缩侧信道风险；对包含 Cookie、CSRF token 或其他秘密的动态响应，部署方仍需按业务决定是否压缩、是否隔离秘密、是否加入随机化或采用其他缓解措施。

### 3. 不能说“所有主流浏览器都支持 zstd”

服务器不能只凭算法名称假设客户端支持 zstd。实际选择必须以本次请求的 `Accept-Encoding` 为准。浏览器、版本、操作系统、代理和中间设备的支持情况可能不同；项目不能把 zstd 当作浏览器必然可解码的编码。

### 4. `s2` 和 `snappy` 不是普通浏览器通用编码

项目按用户设计保留 `s2` 和 `snappy`，并把它们纳入六算法协商。但它们在本项目中是双方约定的扩展编码，不应写成公网浏览器或任意 HTTP 服务的普遍能力。只有请求方声明接受，或使用 `*`，项目才会在本地选择它们；如果请求完全没有 `Accept-Encoding` 字段，则按照 RFC 9110 的默认语义视为任意编码可接受，但项目自身通常仍选择 identity。向配置的上游发送六种编码是项目的两跳协商策略，不代表上游一定实现这些扩展。

### 5. 项目固定顺序覆盖正数 q 值的大小，但不覆盖 q=0 拒绝

项目现在把合法 q 值拆成两种语义：q=0 是客户端明确拒绝，任何 q>0 都只表示客户端支持，正数之间不再比较大小。只要 zstd 的 q 大于 0，即使 `br;q=1`、`zstd;q=0.00001`，仍按项目顺序选择 zstd；如果 zstd 是 q=0，则跳过 zstd，继续按固定顺序寻找下一个 q 大于 0 的编码。这个行为是项目策略，不是 RFC 9110 的通用服务器偏好规则。

目标连接同时固定编码列表顺序和显式 q 权重：`zstd;q=1.000, s2;q=0.999, snappy;q=0.998, br;q=0.997, deflate;q=0.996, gzip;q=0.995`。首项也必须显式带 `q=1.000`，不能依赖“缺省 q=1”的解析差异；列表顺序用于兼容只看排列的服务器，递减 q 用于兼容按权重选择的服务器。普通目标服务器可以因此按项目顺序选择其支持集合中的最高项，但代理不能强制一个完全忽略 `Accept-Encoding` 或自行固定编码的外部服务器。

### 6. qvalue 不能用宽松浮点解析代替 RFC 语法

`strconv.ParseFloat` 会接受 `NaN`、指数形式等非项目允许的输入。当前解析器拒绝 `NaN`、指数、符号和超出 `0..1` 的值，但允许 `0.00001` 等任意精度的小数；非法项目被忽略，不会参与支持判断。重复的同名编码按更严格的最小 q 值处理：q=0 仍能保留拒绝效果，多个正数合并后只要仍大于 0 就按项目固定顺序选择。

### 7. identity 和 wildcard 的边界不能只在“压缩开启”时检查

`identity;q=0` 或适用的 `*;q=0` 不仅影响“是否使用压缩”，也影响不可压缩响应、过短响应、Range、压缩关闭和未知长度响应。当前响应包装器在无法提供可接受编码时返回 406，而不是把原文静默当作 identity。没有 `Accept-Encoding` 字段和显式空字段也必须区分：前者按 RFC 视为任意编码可接受，后者不希望内容编码，但 identity（无编码）仍是可用的表示方式。

### 8. Nginx 示例不能泛化为所有 Nginx

`zstd on;`、`brotli on;` 等指令依赖具体版本和第三方模块，不能当作所有 Nginx 安装的通用配置。历史会话把模块存在、模块指令、浏览器支持和服务端选择器混为一谈；本项目的 Go 适配层不依赖 Nginx 模块。

### 9. 无依据的百分比不应写成项目事实

“99% 的 HTTPS 流量使用某算法”“Brotli 固定高出某百分比”“zstd 对所有客户端都更快”等说法没有给出可复现的数据集、客户端分布、压缩等级、内容样本和测量方法。它们不能作为本项目的兼容性或性能保证，已从修复结论中剔除。

### 10. SDCH 的历史描述不能绝对化

SDCH 是历史上的共享字典方案，不能简单写成“被 Brotli 彻底取代”并据此推导当前客户端行为。项目当前不实现 SDCH，也不把历史浏览器实验特性当成协商依据。

### 11. DoH/DoH3 与原生 DNS 传输必须区分

DoH 和 DoH3 是 HTTP 请求，因此可以使用 HTTP `Content-Encoding`。UDP、TCP、DoT、DoQ 传输的是 DNS wire message 或其对应的 TLS/QUIC 承载，不使用 HTTP `Accept-Encoding` / `Content-Encoding`。把三种 HTTP 压缩直接套到所有 DNS 数据包上是错误的。

### 12. 上游响应不能在未经处理时一律透传

普通反代现在对已知上游编码先解码，再按照本地客户端的 `Accept-Encoding` 重新编码；这样正文改写、ETag、Content-Length 和 Content-MD5 才有一致语义。项目选择编码时忽略所有正数 q 的大小，只按固定顺序选择；q=0、显式空字段或未命中 `*` 时仍表示拒绝。项目不认识的扩展编码不能被本地解码，只能在客户端允许的情况下保留；若客户端完全没有 `Accept-Encoding`，项目仍保持原有的 identity/透传边界，不把缺少请求头当作客户端已声明支持六种编码。

## 当前实现的真实路径

### 普通 HTTP、HTTP/2、HTTP/3

1. 普通 HTTP 反代转发请求时保持请求体、`Content-Encoding`、`Content-Length`、`ContentLength` 和 `TransferEncoding` 的原始语义，不在未获 UI 明确授权时擅自解码或重封装；DoH/DoH3 入口仍在自己的 DNS wire message 边界内处理请求编码。
2. 只有非 API passthrough 且确实需要正文改写、HEAD/Range/WebSocket 特殊表示控制时，才向上游调整 `Accept-Encoding`；API passthrough 保留调用方的协商头。
3. 已知上游响应编码先由公共解码器解码；客户端响应再由 `HTTPResponseWriter` 按“q>0 表示支持、固定顺序选择”的规则独立选择编码。
4. 选择编码后清理 `Content-Length`、`Content-MD5` 和旧 `ETag`，并加入 `Vary: Accept-Encoding`。保留上游未知编码时也加入 `Vary`，但不强行套第二层编码。
5. 正文改写前会跳过压缩流、未知长度、SSE、multipart、WebSocket、Range、`Content-Range`、HEAD、204 和 304 等特殊语义。
6. 普通反代对 HEAD 上游请求要求 identity，避免把 GET 表示的压缩元数据误当成可解码的 HEAD 实体；API passthrough 跳过正文改写并保留调用方的请求体和目标侧协商语义。

### DoH/DoH3

- 本地 DoH POST 请求接受项目六种 `Content-Encoding`，解压后的 DNS wire message 不得超过 65535 字节；不支持的请求编码返回 415，并通过 `Accept-Encoding` 列出六种编码。
- 本地 DoH/DoH3 响应使用公共 HTTP 响应包装器，按请求方 `Accept-Encoding` 的支持集合和固定顺序选择编码，并保留 `Vary: Accept-Encoding`；本地选择与目标 DoH/DoH3 选择相互独立。
- 目标 DoH/DoH3 使用项目自有纯 Go HTTP upstream，显式发送六算法 `Accept-Encoding`，收到响应后由公共解码器处理；没有把 `dnsproxy` 的内部 HTTP client 当作压缩实现。

### UDP、TCP、DoT、DoQ

这些入口仍处理 DNS wire message，不走 HTTP 内容编码协商。不要因为 DoH/DoH3 支持压缩，就把 `Accept-Encoding` 加到原生 DNS 传输上。

## 六种算法与本地源码

用户指定的平局顺序完整保留：

```text
zstd > s2 > snappy > br > deflate > gzip
```

| 算法 | 项目角色 | 本地源码/版本 |
| --- | --- | --- |
| zstd | HTTP 标准生态中有规范定义的内容编码；默认等级 8 映射到 `SpeedBetterCompression`，窗口不超过 32 MiB | `compression/source/klauspost/compress`，`github.com/klauspost/compress v1.19.2` |
| s2 | 项目约定的扩展编码 | 同上，使用 `s2` 包 |
| snappy | 项目约定的扩展编码 | `compression/source/snappy`，`github.com/golang/snappy v1.0.0` |
| br | Brotli 内容编码 | `compression/source/brotli`，`github.com/andybalholm/brotli v1.2.2` |
| deflate | HTTP 内容编码 | `klauspost/compress` 的 flate/zlib 相关包 |
| gzip | HTTP 内容编码 | `klauspost/compress` 的 gzip 包 |

当前本地快照的近似规模为：klauspost/compress 125 个 Go 文件、约 1.13 MB；Brotli 81 个 Go 文件、约 2.55 MB；Snappy 7 个 Go 文件、约 32 KB。源码目录包含许可证和模块文件，业务适配代码集中在 `compression/Compression-algorithm/`。源码体积不等于最终二进制增量，发布大小仍应以 Linux 构建产物为准。

## 本次实际修复

- 严格实现项目 q 参数解析，拒绝 `NaN`、指数、符号和超范围输入；允许任意精度的 `0..1` 小数，q>0 的大小不参与算法选择。
- 目标广告头同时锁定六算法的列表顺序和显式递减 q 权重，首项固定输出 `zstd;q=1.000`；核心选择不依赖可变的公开顺序快照。
- 严格处理编码参数：`Accept-Encoding` 项只接受唯一的 `q=` 参数；`gzip;q`、`gzip;foo=bar`、重复 q 参数等非法项不会被当成默认 q=1 放行。合法 q>0 的大小不参与选择，q=0 才表示拒绝。
- 合并重复的 `Accept-Encoding` 和 `Content-Encoding` 字段；重复 q 值按最小值处理，以保留 q=0 的拒绝语义。
- 正确处理 `identity`、`*`、显式空字段、未知编码和 406/415 边界，同时保留六算法和既定优先级。
- 增加 `ContentEncodingAcceptableValues`，保留“字段不存在”和“字段显式为空”的区别。
- 已知上游编码先解码，重新编码时清理旧实体对应的长度、校验摘要和强 ETag；保留未知编码时补 `Vary`，不强行重新编码。
- 未知长度响应增加首段缓冲：短响应结束时走 identity，达到阈值或调用 Flush 时再确定压缩；不影响 SSE、multipart、WebSocket 和 Range 特殊路径。
- 修复解压上限的精确边界：恰好达到上限允许正常 EOF，确实多出一个字节才返回 `ErrDecodedSizeLimit`。
- HTTP zstd 编码器和解码器均限制 32 MiB 窗口；这是对用户要求 36 MiB 的合法幂次取整，解压输出仍另受规则内存上限或 DoH 65535 字节上限约束。Brotli 使用标准 `lgwin=24`（约 16 MiB），Deflate/Gzip 固定约 32 KiB，S2/Snappy 的块大小不等于 zstd 窗口。
- DoH/DoH3 不支持的请求编码改为 415，并返回六算法 `Accept-Encoding`。
- 规则集探测改为复用公共解码器，支持正确的多层编码、`x-gzip` 别名、统一解压上限和 HTTP zstd 窗口限制；规则集自身仍只向上游请求 gzip、deflate、zstd。
- 正文改写跳过 HEAD、204、304、Range 和 `Content-Range`，避免改写没有实体或部分实体。
- 普通非 API HEAD 请求向上游要求 identity，保留 HEAD 的表示元数据语义。
- 第三方源码快照增加 `compression/source/README.md`，记录版本、包用途、许可证和维护边界。

## 本次新增的双向算法选择

在保留原有六种算法解码、编码和正文处理能力的前提下，反向代理规则现在为本地监听和目标连接各保存一组独立设置。两侧固定顺序均为 `zstd > s2 > snappy > br > deflate > gzip`，默认六种全部启用；前端只在 `http`、`https`、`h2`、`h3`、`dns_doh`、`dns_doh3` 上显示对应控件，WS/WSS 和 UDP、TCP、DoT、DoQ 不显示。

本地监听侧的算法集合限制响应包装器依据客户端 `Accept-Encoding` 选择的编码；目标连接侧的算法集合限制发送给上游的 `Accept-Encoding`。选择“关闭”时只删除对应方向的请求头，六种算法控件变灰但保留原勾选；取消“关闭”后可继续使用原集合。两侧状态互不共享，正文改写、HEAD、Range、WebSocket、请求体解码和 DNS wire message 处理仍沿用原有分支。算法全部取消但未勾选“关闭”时保存为空算法集合，使用独立于关闭标记的文本哨兵，以便编辑回显仍能区分这两个状态。

兼容规则如下：旧客户端缺少布尔字段时按启用处理，缺少算法数组时按六种全选处理；旧数据库中压缩字段为空时按历史六种全开处理；显式关闭和显式空算法集合分别使用不同的存储值。后端对不支持压缩的协议强制保存为关闭/空列表，但不会删除后台对全部六种算法的编解码能力。

前端实现集中在 `temp_frontend/src/components/SettingsReverseProxyManage.vue`、`SettingsReverseProxyManage.shared.ts` 和 `src/types/reverseProxy.ts`；后端字段位于 `database/model/reverse_proxy.go`，运行时请求头和响应协商位于 `service/reverse_proxy_compression.go`、`service/reverse_proxy.go`、`service/reverse_proxy_dns*.go`。验证必须覆盖新建默认值、编辑回显、关闭/恢复、单项取消、协议切换、DoH/DoH3 显隐、移动端布局，以及本地与目标两侧独立保存。

## 仍需部署方确认的风险

1. `s2` 和 `snappy` 虽然在项目中完整实现并参与协商，但公网浏览器和第三方 HTTP 服务不一定实现；应只在双方可控的链路上配置或验证。
2. 浏览器对 zstd 的支持不是静态保证，必须以实际 `Accept-Encoding`、客户端版本和中间设备行为为准。
3. 压缩会消耗 CPU、编码器内存和连接生命周期；当前默认策略是固定后端策略，不是针对每条规则的动态性能自适应。生产环境仍应观察高并发、长响应、HTTP/2/HTTP/3 流量和移动端 CPU。
4. RFC 9110 对“没有 Accept-Encoding 字段”的默认语义较宽，允许任意内容编码。项目不认识的上游扩展在该情况下可以保留，但真实客户端可能仍无法解码；如果部署环境有这类客户端，应在边缘入口明确发送 `Accept-Encoding: identity` 或允许的编码集合。
5. 应用层压缩不能替代动态秘密保护。包含 Cookie、CSRF token 或其他秘密的响应仍需按业务评估 BREACH 类风险；不能因为 TLS 已启用就默认安全。
6. 第三方源码是本地快照。升级版本时必须同步核对许可证、窗口限制、纯 Go 构建、amd64/arm64 汇编文件和所有定向回归；不能只替换单个 `zstd` 子目录。
7. 本轮未运行完整 service 或全仓库测试。若后续修改影响反代 listener、缓存、正文改写资源池、数据库恢复或前端页面，仍需按侧边栏开发手册的定向验证边界在 Linux 目标环境补测。

## 最终判断

历史会话中“HTTPS 压缩”“所有浏览器支持 zstd”“六算法属于统一 HTTP 标准”“服务端 q 值大小决定项目优先级”“DoH 与 UDP DNS 共用 HTTP 压缩”等表述均不能继续作为项目事实。当前实现按用户指定的六算法固定顺序处理所有 q>0 的候选，q=0 仍是明确拒绝；本地监听与目标连接分别独立选择，再把它们放回正确的 HTTP 内容编码、代理两跳解码/重编码和 DNS 协议边界中。最终兼容性仍由请求头、上游能力、客户端解码能力和部署环境共同决定，不能只看算法名称或一条配置示例。

## 2026-08-23 透明反代修补

普通 HTTP/H1.1/H2/H3 请求体保持不透明：反代不调用请求体解码器，不删除 `Content-Encoding` 或 `Content-Length`，不把 `ContentLength` 改成 `-1`，也不主动重建请求实体。DoH/DoH3 的 DNS wire message 仍在 DNS 专用入口处理编码。

`ApiPassthrough` 现在同时保护上游响应表示：跳过普通 HTTP 响应解码和本地重新压缩，保留上游的编码、长度和实体摘要；URL 路径映射仍只处理 `Location`、`Content-Location`、`Link`、`Refresh` 与 `Set-Cookie` 等 URL 语义头，不再对任意自定义响应头做字符串替换。

路径前缀裁剪会保留 `RawPath` 中的百分号编码，例如 `%2F` 不会被还原成路径分隔符。客户端传入的 `Forwarded`、`X-Forwarded-*` 和 `X-Real-IP` 默认保持原值，不再由普通反代隐式清理重建；HTTP hop-by-hop 头仍遵循标准 `ReverseProxy` 的连接级转换规则。

本轮默认压缩等级按算法分开：zstd 使用等级 `8`，Brotli、S2、DEFLATE/Gzip 使用等级 `6`，Snappy 不使用数值等级。zstd 的用户目标窗口为 36 MiB，但底层编码器要求窗口为 2 的幂，因此实际取不超过目标值的 32 MiB；Brotli 使用标准最大 `lgwin=24`（约 16 MiB）。Deflate/Gzip 的 32 KiB 格式窗口以及 S2/Snappy 的固定块边界不能安全扩展为 36 MiB。窗口和编码器缓冲均按数据流动态增长，响应结束关闭编码器后释放，不在服务启动时预分配整块内存。
